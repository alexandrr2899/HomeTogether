# Integración de Jaime con OpenClaw en mewtwo

**Estado:** Home Together usa en desarrollo el agente existente `main` de OpenClaw, el mismo que atiende Telegram. El Gateway de mewtwo permanece en loopback y exige token. Lugia llega a él por un túnel SSH local en `127.0.0.1:18790`. Una skill `hometogether` instalada en `main` consulta el backend de lugia por un segundo túnel local: en pruebas reales con la sesión de Lastenia se verificaron listas, bienestar autorizado de Alexander, agenda y presencia. Los túneles y el servidor Django de desarrollo deben estar activos; el enlace definitivo para Portainer sigue pendiente.

## Flujo elegido

```text
Móvil o tablet → sesión/CSRF de Django → turno temporal ligado a Alexander o Lastenia
                                     → Gateway de OpenClaw, agente main
                                       → skill hometogether → herramienta interna exec
                                         → script local con token de servicio
                                           → ruta privada de Django → adaptadores existentes
                                     ← respuesta de Jaime
```

La interfaz habla únicamente con Django. Django identifica al usuario mediante la sesión y llama a `POST /v1/chat/completions` del Gateway con `openclaw/main`. Si el puente está configurado, crea un `BridgeTurn` de tres minutos, indica su UUID al agente y no ofrece funciones HTTP aportadas por el cliente. La skill llama a la ruta `/api/v1/jaime/bridge/` con ese UUID y un token de servicio guardado fuera del repositorio. Django recupera el actor del turno, exige que siga siendo administrador, limita a seis operaciones, valida argumentos mediante `chat_tools.py` y caduca el turno al terminar la respuesta. Solo puede preparar una propuesta pendiente por turno; la respuesta del chat incluye su ID para mostrarla en la interfaz. Los turnos antiguos se eliminan después de un día; conservan actor, hora, cantidad, última operación y el vínculo con la propuesta, nunca valores consultados. El script de OpenClaw no recibe credenciales de Home Assistant ni Google. [Contrato HTTP de OpenClaw](https://docs.openclaw.ai/gateway/openai-http-api).

La configuración real usa `agents.entries` y contiene únicamente `main`; `GET /v1/models` devolvió `openclaw`, `openclaw/default` y `openclaw/main`. Una petición autenticada de prueba a `openclaw/default` devolvió HTTP 200 y la respuesta esperada, sin llamadas de función. Home Together configura `HT_OPENCLAW_AGENT_ID=main` y solo declara la conexión activa cuando ese modelo aparece en `GET /v1/models`.

Las funciones que Home Together ofrece en la petición HTTP **no limitan las herramientas internas del agente OpenClaw**. El usuario quiere que Jaime sea un asistente general: `main` conserva el perfil global `coding` y sus capacidades actuales. Por ello, la confirmación que exige Django aplica a las `ActionProposal` de Home Together; una acción ejecutada por una herramienta propia de OpenClaw sigue las reglas de OpenClaw y no pasa por esa confirmación. La interfaz indica expresamente esta diferencia.

La vía anterior de funciones aportadas por el cliente HTTP no produjo `tool_calls` en OpenClaw 2026.9.6; una función exigida devolvió HTTP 502. Esa vía queda como compatibilidad solo si no hay token de puente. Con la skill instalada, las cuatro **lecturas** y la creación de una **propuesta pendiente** sí se verificaron desde la ruta privada de chat de Django con sesión y CSRF. La skill nunca confirma la propuesta: esa acción sigue separada en Home Together.

Se probó también una **skill temporal** en el espacio de trabajo de `main`, sin datos familiares. OpenClaw la declaró elegible y el agente respondió con una palabra conocida solo por la skill. La skill **no** logró invocar una función `prueba_tecnica` aportada por el cliente HTTP; el agente indicó que esa función no estaba disponible. Una segunda versión de la misma skill sí usó la herramienta interna `exec` para ejecutar un `printf` inocuo y devolvió el texto esperado. Después se borró la skill y se comprobó que dejó de figurar en el inventario. Esto demuestra que una skill puede guiar herramientas internas, pero no resuelve por sí sola la identidad de Alexander o Lastenia ni la autorización de operaciones en Django. Un puente real necesitaría autenticación entre servicios y un vínculo verificable con la sesión de Home Together; los secretos no irían en `SKILL.md`. [Creación y carga de skills](https://docs.openclaw.ai/tools/creating-skills), [herramientas internas](https://docs.openclaw.ai/gateway/config-tools/tool-policy).

Después se completó una **prueba real de lectura por skill**. Un servidor temporal en lugia usó el servicio existente `apps.lists.service.read_lists()` de Django, protegido por un token aleatorio y un túnel SSH inverso limitado al loopback de mewtwo. Su respuesta contenía solo ID, estado y número de pendientes de las tres listas; nunca títulos ni UID. La skill temporal `hometogether-probe` indicó al agente `main` ejecutar un script interno que consultaba ese servidor. La llamada directa al script y la respuesta posterior de OpenClaw coincidieron con la lectura real de Home Assistant: Compras 2, Súper 4 y To-do 0 pendientes en ese instante. La respuesta del agente tardó alrededor de 11 segundos; no se midió una latencia de sincronización Alexa → Home Assistant. No hubo escrituras. Se retiraron la skill, el script, los dos archivos de token, el servidor y el túnel de prueba; `openclaw skills info` dejó de encontrarla. Esto **verifica el recorrido de solo lectura** OpenClaw skill → herramienta interna → puente temporal → Django → Home Assistant, pero no una integración persistente ni permisos por cuenta.

No se añadió otro agente ni un binding de Telegram. OpenClaw mantiene un único agente `main`, y la ruta implícita de Telegram conserva su configuración actual. Las conversaciones de Home Together usan un identificador estable distinto por cuenta y conversación; esto separa sesiones de chat, aunque comparten el agente y su espacio de trabajo. [Sesiones HTTP de OpenClaw](https://docs.openclaw.ai/gateway/openai-http-api).

En el alcance verificado de la skill, las operaciones son agenda acotada, listas, presencia, bienestar autorizado y preparación de propuestas para añadir a To-do, añadir a Compras o completar una tarea. `allow_jaime` debe estar activo para consultar indicadores Garmin; otra cuenta solo puede pedirlos si figura en `jaime_viewers`. Esto no los muestra en Inicio. El puente rechaza cualquier otra escritura y limita a una propuesta por turno. Confirmar la propuesta requiere el endpoint separado de Home Together con sesión y CSRF. Estas reglas no gobiernan otras herramientas internas de OpenClaw; futuras acciones del hogar requerirán entidades y operaciones permitidas expresamente en Django.

Django trata los argumentos del agente como entrada no confiable: valida operación, intervalo, lista, persona y permisos. El script solo admite comandos cerrados y se comunica con un destino fijo en loopback; rechaza redirecciones y respuestas mayores de 20 kB. Un texto generado no confirma una escritura. El identificador `user` de OpenClaw se separa por cuenta y conversación; no comparte una sesión de Home Together entre Alexander y Lastenia. [Sesiones en la API de chat](https://docs.openclaw.ai/gateway/openai-http-api).

## Red entre Portainer y el host

`localhost` dentro del contenedor Django apunta al contenedor, no a mewtwo. En Linux, Compose puede añadir `extra_hosts: ["host.docker.internal:host-gateway"]` al **backend**; Django llamaría, por ejemplo, a `http://host.docker.internal:18789`, siempre que esa dirección resuelva a una interfaz donde escuche el Gateway. El valor `host-gateway` suele resolver a la IP del bridge predeterminado del host, que se comprobará en mewtwo antes de fijar la URL. [Redes de Docker Compose](https://docs.docker.com/compose/how-tos/networking/).

La inspección directa en mewtwo confirmó un bind solo a `127.0.0.1` y `[::1]`. En ese estado, el contenedor **no puede** alcanzarlo mediante `host.docker.internal`: la petición llega a la IP del bridge, no al loopback del host. Para producción se estudiará un proxy local restringido a la interfaz Docker que reenvíe a loopback; así se conserva la configuración actual del Gateway. También puede evaluarse un bind específico del Gateway si la red real lo exige. Se verificará que el puerto no sea público y que Telegram siga funcionando. No se pondrá `bind: "lan"` a ciegas. [Modos de bind de OpenClaw](https://docs.openclaw.ai/gateway/config-gateway), [exposición de red](https://docs.openclaw.ai/gateway/security/network-exposure).

El proxy **en el host** escucharía solo en la interfaz Docker y reenviaría a `127.0.0.1:18789`, idealmente limitando las rutas a `/v1/models` y `/v1/chat/completions`. Se elegirá al preparar Portainer, después de identificar la red real. El teléfono seguirá entrando solo al dominio HTTPS de Home Together; nunca llamará al Gateway directamente.

En sentido inverso, el `compose.prod.yml` publica el backend solo en el loopback de mewtwo, `127.0.0.1:18005:8000`. El script instalado en OpenClaw llama exclusivamente a `http://127.0.0.1:18005/api/v1/jaime/bridge/`. Nginx devuelve 404 para esa ruta en el frontend público. El backend exige además el token de servicio y un turno vigente. En desarrollo, un túnel SSH inverso conecta ese puerto de mewtwo con `127.0.0.1:8005` de lugia. Este túnel y el servidor de desarrollo se perderán al cerrar sus procesos o reiniciar; el mapeo de Docker será el enlace permanente cuando se despliegue en mewtwo.

Para restablecer los túneles de desarrollo desde lugia se usa la identidad SSH dedicada y `IdentitiesOnly=yes`; sin esas opciones el servidor puede rechazar las claves ofrecidas por defecto:

```bash
ssh -i /home/alexandrr/.ssh/id_ed25519_mewtwo_hometogether -o IdentitiesOnly=yes -o ExitOnForwardFailure=yes -N \
  -L 127.0.0.1:18790:127.0.0.1:18789 \
  -R 127.0.0.1:18005:127.0.0.1:8005 alexandrr@10.0.0.63
```

## Secretos

En lugia, el token está en `.env` con permisos `0600`. En producción se guardará en la configuración privada de Portainer y se entregará solo al backend. Es una credencial de operador del Gateway, **no** un token limitado a Home Together; la red se restringirá entre Django y el Gateway. No se pondrá el token en React, Git, logs o mensajes. El acceso a Jaime seguirá limitado a las dos cuentas administradoras de Home Together. [Límite de seguridad de la API HTTP](https://docs.openclaw.ai/gateway/openai-http-api), [política de herramientas](https://docs.openclaw.ai/gateway/config-tools/tool-policy).

El puente de lectura usa un **segundo token**: `HT_JAIME_BRIDGE_TOKEN` en Django y el mismo valor en `~/.openclaw/hometogether-bridge.token` con permisos `0600` en mewtwo. El archivo `openclaw/hometogether/SKILL.md` y su script se versionan sin credenciales. El token no se imprime ni se pasa como argumento del comando; se rota actualizando ambos destinos. Como `main` conserva `exec` sobre su propio host, el archivo no es una frontera frente a herramientas del mismo agente: el control efectivo de datos lo aplica Django por turno y usuario.

Las consultas de Jaime envían al Gateway el texto del usuario y los resultados que la skill lee de Django, que pueden incluir agenda, listas o bienestar autorizado. Antes del despliegue de Home Together en mewtwo habrá que revisar el proveedor de modelo, la retención del historial y quién puede acceder a esas conversaciones. La pantalla actual mantiene los mensajes solo en memoria mientras permanece abierta; la sesión del Gateway puede conservar contexto según su configuración.

Alexander autorizó que Lastenia consulte sus indicadores Garmin mediante Jaime. La autorización se registra por destinatario en Django y se puede revocar en Configuración; no activa el bienestar compartido en Inicio. El ajuste `allow_jaime` y la lista de destinatarios controlan únicamente la función de bienestar de Django. La configuración revisada de OpenClaw no declara un complemento ni un servidor MCP de Home Assistant. Sí mantiene el perfil general `coding`, que incluye herramientas fuera del control de Django; por ello, estos ajustes no constituyen una barrera global contra otras vías de acceso. Esta limitación se muestra en Configuración.

## Activación y verificación

1. **Verificado en desarrollo:** `main` y la skill `hometogether` están disponibles en mewtwo. Desde la ruta Django `/api/v1/jaime/chat/`, con sesión de Lastenia y CSRF, cada consulta generó un turno ligado a ella; `last_tool` confirmó exactamente `consultar_lista`, `consultar_bienestar`, `consultar_agenda` y `consultar_presencia`, una llamada por turno. Las respuestas numéricas fueron 2 pendientes en Compras, 4 indicadores Garmin de Alexander, 0 eventos en dos días y 2 personas con presencia disponible en esas lecturas. No se imprimieron títulos, mediciones ni ubicaciones. Los turnos caducaron al finalizar.
2. **Permisos comprobados en pruebas aisladas:** sin token se rechaza la ruta; también se rechazan acciones no permitidas, UUID desconocido, turno caducado, cuenta que pierde administración y más de seis llamadas. La lectura de Garmin aplica `allow_jaime` y `jaime_viewers`. Una segunda petición de propuesta en el mismo turno devuelve el ID ya creado sin duplicarla. No se ha probado un cambio de permisos en mitad de una conversación real.
3. **Pendiente para Portainer:** desplegar las imágenes y comprobar desde el contenedor el enlace privado hacia el Gateway. La dirección `host.docker.internal` por sí sola no llega al Gateway actual en loopback. Comprobar también desde OpenClaw el puerto `127.0.0.1:18005` publicado por el backend, con el token de producción. En desarrollo, la configuración de Nginx ya devolvió 404 en `/api/v1/jaime/bridge/` con y sin barra final; falta verificarlo en el despliegue.
4. **Consultas desde navegador verificadas:** el navegador real abrió Jaime a 390 px con sesiones temporales de ambas cuentas sin errores ni desbordamiento. Tras restaurar los túneles SSH usando la identidad dedicada, ambas cuentas enviaron una consulta de Compras y recibieron respuesta. Django registró una llamada `consultar_lista` por cuenta, ligada a su actor y caducada al terminar. No se imprimieron títulos de ítems. Sigue pendiente evaluar qué contenido queda en el historial de OpenClaw.
5. **Propuesta, confirmación y retirada verificadas en navegador:** Lastenia pidió a Jaime preparar un único ítem temporal autorizado en Compras. La propuesta apareció como pendiente sin ítem externo; al pulsar Confirmar en Home Together, Django la registró como `confirmed` y Home Assistant mostró exactamente un ítem después de unos 4 segundos. El usuario confirmó que también apareció en Alexa. Se abrió el ítem por su nombre en Organizar y se eliminó desde allí; Home Assistant confirmó cero coincidencias tras unos 3,6 segundos y una segunda lectura también devolvió cero. La ausencia final en Alexa espera confirmación manual. No se crearon duplicados. La voz sigue pendiente; Alexa refleja la lista, pero no se ha verificado que pueda abrir una conversación con Jaime.

El `compose.prod.yml` añade `host.docker.internal:host-gateway` únicamente al backend, publica el backend para OpenClaw solo en loopback y admite ambos tokens mediante variables privadas de Portainer. Las variables de producción quedan vacías hasta preparar el enlace al Gateway. OpenClaw seguirá fuera de Portainer y Home Together permanece en lugia durante el desarrollo.

En lugia se comprobó el cliente HTTP contra un Gateway local de prueba: descubrimiento del agente, autenticación y respuesta con llamada de función. Configuración muestra el estado del Gateway con una comprobación acotada a tres segundos. La conversación y la skill sí se verificaron después con el Gateway real de mewtwo; las llamadas de función **aportadas por el cliente HTTP** siguen sin funcionar en esta versión y no se usan cuando el puente está configurado.
